Topic1：Harness–Engine 协同框架

组件化候选方案与数据使用计划 · 2026-10-19 · 尚待实验验证

2026-10-28 当前焦点：转向真实 Harness 生命周期，优先审计上下文交接与父级唤醒，等待实例驻留作为有条件后备。查看 一般动作、候选痛点与实验准备。下方三组件框架及 此前收敛复审 保留为历史候选；排队演示 不承担当前研究动机。

目标：让 Agent Harness 对工作流的了解，与推理引擎对 KV、队列和资源压力的观测共同影响任务推进。候选框架由三个功能组件组成，共用一个计划选择器；HEAR 是双向协同的关键参照。

三个组件

① 工作流推进

决定哪些已获准调用现在启动、继续或分波执行；考虑依赖、等待和任务阶段。

② 跨轮 KV 状态管理

为候选调用安排精确历史的保留、换出、恢复或重算，并把恢复时机与准入安排关联。

③ 预期执行

管理尚未正式就绪的未来候选：能提前做多少、何时采用或作废；输入未知时只估计需求。

如何协同

每个候选计划包含“下一波正式工作、对应 KV 路径、可选未来动作”。选择器在 GPU/CPU KV、计算、传输和工具并发等独立资源约束下比较计划；引擎保留实际 batch 与 token 调度权，并反馈执行结果。

数据集与用途

数据 / 基准包含什么后续怎么用边界
CacheWise Coding Traces94 个脱敏会话；原始轨迹共 35,127 条记录。公开解析结果含 20,634 次 LLM call、11,617 次 tool call。先做机会审计和 trace-driven 系统回放：保留完整会话顺序、工具等待与请求长度，分析缓存竞争，再比较调度和 KV 路径。原始记录有对话文本；解析事件主要保留 token/cache 用量、工具类型与时序。工具参数已脱敏，没有可加载的模型 KV。不同模型要用目标 tokenizer 重算长度。
SWE-bench + OpenHands代码仓库 issue 修复任务与测试环境，形成多轮读写、运行测试和继续修改的编码工作流。作为主要端到端验证：运行真实 Agent，自由生成并按测试评估任务解决率，同时测完成时间、P95、吞吐与 KV 成本。任务执行成本高，先用完整任务做小规模机制验证；不可把 trace 回放指标当作代码正确率。
SCBench长上下文、多轮请求的缓存评测负载。单独检验长前缀和跨轮请求的状态管理；与工具型工作流结果分开报告。覆盖长上下文服务，不代表 coding agent 的工具依赖与分支执行。
BrowseComp-Plus / DeepResearchBench + Open Deep Research多步检索与研究任务，包含 Main/Reader 等多角色协作。作为第二类工作流，检验并行任务分波、依赖汇合与跨会话资源竞争，并用原基准质量指标评估。运行成本较高，放在核心 coding 机制成立后做通用性验证。
CacheWise 时间戳注意：轨迹时间字段落在 2020 年，但记录中的模型 ID 属于 2025 年；仓库没有说明日期归一化规则。先只使用单会话内事件顺序和相对间隔，不将绝对日期用于到达率或现实日历结论。

实验使用顺序

  1. 审计 workload：按完整会话抽取请求长度、工具种类、等待时间、上下文增长和可观察的未来工作，判断三个组件分别有没有真实机会。
  2. 系统回放：按原会话顺序保留事件；需要并发时从完整会话构造并发组合，不截断历史、不拼接成伪任务。用回放比较原生调度、独立策略与共同计划，测 TTFT/JCT、goodput、命中、淘汰、搬运和重算。回放只验证系统行为，不评价任务答案。
  3. 端到端任务：在 SWE-bench/OpenHands 上运行真实任务并使用测试结果评价质量；再用 SCBench 和研究工作流检查不同 workload 下是否仍成立。

CacheWise 的对话记录可帮助构造输入，但其工具参数已脱敏、时间戳含义未确认，且没有可复用 KV 文件；因此它适合做负载审计和受控系统回放，任务质量结论应来自实际 benchmark。
