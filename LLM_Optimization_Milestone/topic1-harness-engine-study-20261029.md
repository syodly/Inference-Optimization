# Topic1：Harness 如何结合引擎状态展开与派发 DAG

2026-10-29。当前问题定义、机会审计与实验方案。**没有运行真实引擎实验，没有测得性能收益，也没有确认新颖性。**

## 核心判断

值得研究的对象是：**Harness 的派发动作既消耗当前推理资源，也决定后续请求何时、以什么结构产生。能否利用这两方面的信息，改善整个用户任务的完成，而不是仅改善单次请求？**

前端知道依赖、汇合条件、尚未展开的分支、工具执行状态和哪些工作可以省略；引擎知道实际队列、KV 驻留、准备成本与执行干扰。这里有三个耦合量：任务语义决定一次执行对任务的价值；引擎状态决定这次执行的边际代价；这次执行的结果又改变未来负载。研究空间应从它们的冲突出发，DSH 只是可选实现载体。

这不是默认的新颖性主张。DAG 调度、动态运行时、资源感知拓扑、缓存与关键路径已经有直接相关工作。最终贡献必须落到一个可复现的失效模式、解决该失效的机制，以及对强基线的净收益。

## 先分清四类决定

| 决定 | 例子 | 实际改变什么 |
|---|---|---|
| 工作流语义 | 必须研究哪些问题；全部完成还是合格一个即可 | 什么结果才算完成、哪些工作合法 |
| Harness 展开 | 一个已授权研究任务现在启动几个分支；何时运行下一轮规划 | 逻辑工作何时变成工具与模型请求；可能影响后续工作集 |
| 请求派发 | 对已经绑定输入的模型调用分波、排序、路由 | 请求到达引擎的时间与位置 |
| 引擎执行 | 准入、chunked prefill、batch、KV、抢占 | 实际资源分配与执行代价 |

“Agent 数量”不是足够明确的动作。必须说明是改变逻辑分支总量、在线实例数、在途请求数，还是引擎同时执行的序列数。一个 Agent 可能反复调用模型，也可能长时间只等工具。

逻辑任务可以已经获准、具备启动条件，但它的下一次模型 prompt 尚未形成。相反，真正请求级 READY 指输入已经绑定、依赖满足，可以送入引擎。两者不能混成同一个队列；未知工具输出不能按已知 prompt 处理。

## 四类根本痛点

### 1. 更高的请求吞吐，未必换来更多完成的任务

**直觉例子。** 任务 A 只差最后一个 researcher 就能汇总；任务 B 刚准备展开多个长上下文分支。先服务 B 可能提高短期 batching 或前缀命中，却让 A 和 B 都长期没有最终结果。也可能反过来：一味追 A 的关键路径，导致大量冷 prefill 和上下文搬运，整机变慢。

前端信号是依赖、join 类型、任务进度和等待；后端信号是实际前缀命中、额外 prefill、KV 占用和混合执行成本。合法动作是从当前已就绪集合中选具体调用、分波、路由，不是强迫所有 child 同时运行。ALL join 不等于 gang scheduling。

**判断：基础矛盾、必须比较的强基线，不宜单独立题。** TOPAS 已联合 prefix residency 与 ready-request admission，并权衡最长剩余服务路径、复用与抢占；SAGA、TokenCake、Coda 也有直接相邻机制。把关键路径和 KV 利用率写进一个分数，不能自动形成新贡献。

### 2. 当前引擎看起来不忙，但已有工作正在制造下一轮负载

**直觉例子。** 两次观测的模型队列、KV 占用相近：一次有多个研究分支在等待搜索返回；另一次没有这批在途工作。此时启动相同的新一轮长上下文研究，可能产生不同结果。只看当前队列的控制器分不清这两个状态。

同样，一个短请求完成，可能让任务结束，也可能释放出多个新分支。只依据本次请求长度或即时关键路径收益排序，可能持续打开新工作，让后续需求积累。反过来，一味限制展开，又可能饿死 GPU、延误工具流水线。

**值得先检验的假设。** 当前合法前沿、已经在工具阶段的工作，以及节点可能释放的后继需求，能否在现有引擎状态之外提供有效信息？这些信息能否帮助选择下一批逻辑工作及模型请求，而不仅是降低可见队列长度？

具体动作可以是：暂缓某个尚未启动的必做分支、允许另一分支先推进、按波次启动、选择下一轮规划与结果汇总的先后。必做分支最终全部执行；不根据负载直接删任务。工具只在启动前且语义允许时延后，不任意中断已发出的外部操作。

在线只使用已揭示依赖、明确的应用规则、当前工具类型与已等待时长、历史返回时间分布。不能知道未来准确输出、真实返回时间或尚未生成的整个子树；预测必须带误差与退化对照。

**判断：首要机会审计对象，尚非已确认创新。** Nalar 已支持动态工作流和可修订调度；TOPAS 不假设未来 ready 时间、ReAct 轮数和未展开工具结果已知；SAGA 已讨论动态图推断和工具长尾。因此不能把“在线”“动态图”本身当差异。经典背压、lookahead 和分阶段流水线调度也应是基线。需要证明：显式考虑尚未提交的需求及展开动作，解决了这些机制组合仍存在的损失。

### 3. 立即并行能减少等待，也会失去先观察结果再决定的机会

**直觉例子。** 一个应用允许生成多个代码候选，但第一个候选可能已经通过公开测试。一开始全部启动能缩短最坏等待；先启动少量、看到失败再展开能省掉部分工作。哪个更好取决于任务难度、验证速度，以及此刻额外一次推理会给其他任务造成多大干扰。

这里改变的是实际工作集，不能与固定工作集调度混报。合法动作由应用明确给出：增加一个候选、进入下一轮、运行 reviewer、在满足有效终止条件后不再展开。在线信号可以是公开测试、明确覆盖要求或应用声明的接受条件；不能把一个任意模型置信度当成最终质量真值。

**判断：第二阶段候选，空间较宽但排重风险高。** INFRAMIND 已按基础设施状态选择初始拓扑、Agent 数与角色，并进行逐步路由；运行中拓扑修订也被明确列为未来方向。Murakkab 的 OSDI 2026 版本 §4.4 已包括动态 coding、并行候选数、review、公开测试驱动的提前终止与后续迭代。不能说这些工作只支持静态 workflow。

可能继续检验的内容是：共享引擎的实际边际成本、部分有效结果与扩展决定是否需要联合控制，以及是否胜过资源感知配置与已有动态终止的组合。仅把候选数从 4 调成 2，或“负载高时少想一点”，贡献不足。

### 4. 每个 Harness 都响应负载，整个系统仍可能一起过度响应

**直觉例子。** 多个 Harness 看到同一份“空闲”快照，各自释放一批工作；随后同时收缩，再同时恢复。平均并发不高，仍可能出现工具返回后的拥塞、任务长尾和不公平。

动作涉及共享准入、每根任务的进度保护、反馈更新频率、过期反馈处理与有限放行。引擎必须拥有最终容量仲裁权：状态观测不是资源承诺。不要为了这个问题默认发明两阶段协议或整组资源预留。

**判断：第一阶段必须覆盖的鲁棒性场景，暂不单独立题。** CONCUR 已有反馈式 Agent 准入；Crossflow 已有短期多资源 lease 与原子记账；Nalar 已将局部事件响应与周期性全局控制分开。多 root、延迟反馈、动态 cap 本身都不是创新。

## 为什么不只在后端做

这是整个方向最重要的反向检验。

如果所有工作已经确定、所有 prompt 都已就绪，前端只把它们按另一顺序送入引擎，那么一个得到相同 DAG 信息的后端调度器通常也有机会实现相同策略。前端排队减少了后端排队，不代表任务真的更快。不能靠不给后端依赖信息，制造“跨层控制”的优势。

前端可能增加的控制能力主要出现在请求形成之前：

1. 尚未展开的分支会先触发工具、上下文准备或下一轮规划；引擎单独延后一个已提交模型调用，未必能阻止这些活动。
2. 一个部分结果可能使其他探索变得不再必要；在请求产生前调整扩展，可以避免整段工作，而不是仅搬动队列。
3. 后继图由运行中输出决定，当前图只部分显露；Harness 可以提供已知规则和不确定性，而不是让引擎从请求到达反推。

这些能力也可能通过带应用回调的后端控制器实现。研究贡献应是信息与动作如何联合使用，而不是策略代码放在哪一层。必须加入“同信息、同动作权限”的强对照；若其结果一样，就不宣称前端位置带来独立收益。

## 建议先做的两个实验

### E1：先验证看见工具中和未展开的工作，是否真的有额外价值

**问题。** 瞬时引擎状态相近，但当前模型请求之外的在途工作不同，是否会改变合适的展开/派发策略？

**工作负载。** 优先采集 ODR 的 supervisor → researchers → 搜索/阅读 → 汇总真实执行。用递归 GPT Researcher 检查逐步展开，用条件检索/CRAG 检查窄前沿，后两者先作为边界，不一次接入所有 Harness。CRAG 的评分与路由模块不是默认独立 Agent。Coding trace 可作外推，但不得把单 Agent coding loop 画成原生多候选并行。

先统计同一任务真实的 READY 宽度、同时在途工具数、后继返回规模、模型/工具各占多少耗时，以及出现资源压力的区间。绘制的是实际执行，不从源码中的 for/gather 或静态 DAG 宽度推定并发。

**最小操控。** 保持模型、原始计划、必做分支、工具及请求集不变；只控制已获准分支何时启动、已绑定调用何时提交。不调 ODR 的 `max_concurrent_research_units` 来冒充纯并发实验：该配置会进入 supervisor prompt，而且当前源码对超出调用返回错误，改变它可能改变计划与实际工作集。固定原配置，使用外层分波；保留原有 overflow 语义。

**先回放、再闭环。** 图回放按依赖释放调用，工具延迟相对前驱实际完成计时，不能保留原始绝对到达时间。录制 prompt/结果的回放只隔离系统效应，不能验证质量或真实闭环行为。固定请求集只适用于这类诊断或受控子图。真实应用执行是后续必要验证：固定应用规则、初始参数与任务级到达，但调整启动与结果顺序仍可能改变未来图。真实闭环必须报告工作量差异，若请求集变化，不能将全部收益归为固定工作量调度。

**比较组。**

| 组 | 可以看见什么 | 可以做什么 |
|---|---|---|
| 原生系统 | 原生应用与引擎各自信号 | 原生 cap 与引擎调度 |
| 引擎压力基线 | 队列、KV、请求大小与执行成本 | 全局请求准入，调优静态/动态并发 |
| 工作流强基线 | 加上依赖、join、已揭示任务进度、前缀 | TOPAS/SAGA 风格进度与缓存调度；Coding 加 Coda 风格成本/兼容性 |
| 在途工作基线 | 再加工具状态、返回分布、已知后继规则 | 简单背压、固定分波、对工具中工作量计账 |
| 候选联合控制 | 与上一组相同信息 | 同时选当前合法工作与下一批展开；暂缓必做工作，不删工作 |
| 同信息后端对照 | 与候选完全相同信息 | 同等请求重排权限；再增加 Harness 回调后比较同等展开权限 |

机制近似不能标为复现原论文。要写明实现与原论文的差别，并调优基线。除上界对照外，没有任何组能提前知道准确工具返回或未生成输出。

**可实现的第一版候选。** 在请求/工具完成、前沿变化与显著容量变化时更新；分开记录当前合法调用、工具中的工作、已获准但未展开的分支。对少量可行波次比较即时服务成本、下一时间窗的预计回流需求和任务推进；只预测一个有限窗口，不先训练复杂 RL。按模型分开记录需求，并给老任务最大等待保护。工具类型/耗时分布、非缓存输入 token 和实际共享 KV 都需单独计量，不能用统一的“每 Agent 一个槽”代替。候选若退化成关键路径加 KV 分数，就按 TOPAS 相邻实现处理。

**最小接口与埋点。** 以下是待实现的实验接口，不是 DSH 或引擎已提供的完整 API，也不是 raw execution data。

| 对象 | 第一版需要的字段或动作 |
|---|---|
| 逻辑工作 | `root_id / node_id / parent_id`、已知依赖、必做/可选、join 条件、逻辑就绪与实际启动时间 |
| 模型请求 | `call_id / node_id / model_id / context_version`、完整 prompt 的可追溯引用、采样与输出上限；输入绑定、前端放行、引擎接受、实际执行、完成时间 |
| 工具 | `tool_id / node_id / type`、开始/结束时间、状态；下一次调用仅在结果产生且输入绑定后标为 READY |
| 引擎状态 | 采样时间、分模型队列与运行请求、可分配 KV、实际命中/新增 KV、prefill 与执行耗时；缺失指标标缺失，不用 UI token 代替 |
| E1 动作 | `release_branch(node_id)`、`submit_call(call_id)`、`defer(item_id, until_event_or_timeout)`；检查依赖与最大等待，不更改必做集合 |
| E2 新增动作 | `expand(optional_group_id, count)`、`stop_optional(group_id, valid_reason)`；仅在应用声明允许且终止条件有效时使用 |

引擎接受不等于开始执行，首次 token 不等于任务完成。事件中同时保存因果 ID 与单调时钟时长；采样视图注明年龄。实际执行前仍由引擎重新核验容量。

**测量。** 从用户任务提交到最终有效结果的耗时，P50/P95；固定质量门槛下按时完成的任务数；前端等待与后端等待总和；实际 prefill、KV 驱逐/重算、工具启动延迟、模型利用率、每根任务最长等待、控制开销。模型计量与 Harness 计量使用关联 ID，分布式时间用可核对的时钟或时长。任务数、分支数、请求数、输入/输出 token 都检查是否改变。

**关键消融。** 去掉工具状态；去掉已知后继规则；只用当前引擎压力；保留信息但只做固定分波；增加预测误差/工具长尾；加入其他 Harness 与延迟反馈；低负载检查是否饿死引擎。预测准确率本身不等于性能收益。

**继续条件。** 在途/展开信息解释了真实损失；经过调优的工作流感知、背压和同信息后端对照仍有剩余差距；收益不是转移排队、减少工作或放松质量。如果 READY 长期接近 1，就不以宽 fan-out 作为该 workload 的动机；应检查阶段衔接或更换有实测依据的 motif。

### E2：只有应用允许可选探索时，才测“先做少量、再决定是否展开”

使用有公开验证信号和独立最终评分的代码任务，固定模型/硬件/候选上限，比较全部启动、串行失败再启动、固定波次、压力感知波次、质量反馈策略，以及资源成本与部分结果联合控制。公开测试只作在线信号，隐藏测试仅离线评分，不能泄露给控制器。

所有策略跑相同的任务级到达过程、评分集与共享资源，报告质量—任务完成耗时—实际成本曲线；预先给出质量非劣容忍度。报告真正少生成了什么，以及省下的工作是否改善其他任务完成。不能把单任务少做一次调用的成本节省直接当成集群吞吐提升。

ODR 的在线研究质量难以可靠判定，第一阶段不以“信息已足够”为由删 researcher。Murakkab 动态 coding 与 INFRAMIND 资源感知配置是此实验的直接近邻；须先比较其机制组合，不能只打固定四候选这个弱基线。

## 近期优先级

1. 主线先做 E1 的真实 trace 机会审计，检验“当前请求之外的工作”是否是重要遗漏信息，再决定是否实现联合控制。
2. E2 保留为有条件扩展：设计空间更宽，但需要质量闭环，且与 Murakkab、INFRAMIND 的差异更难建立。
3. 请求优先级/KV 感知、简单动态并发、结果通知合并、DSH 槽位和 fork/spawn 使用选择保留为基线或实现背景，不各自发展成主线。

通用性来自跨应用重复出现的结构：产生后继的节点、工具间隔、汇合、可选探索。不是来自一开始兼容尽可能多的 Harness。前两个 workload 证明相同机制、一个窄前沿 workload 明确无效边界，比铺满十种场景更有说服力。

## 已核查的主要来源

以下“已有”描述来自原文；上面的痛点例子和候选控制均是待验证假设。2026-10-29 再次在线核对了 arXiv 题目及部分全文；本地既有快照、页码与代码另行交叉核对。

- [INFRAMIND，2606.11440](https://arxiv.org/abs/2606.11440)：初始拓扑/角色/Agent 数、逐步模型与推理模式、预算调度；结论的 limitations 明确讨论 runtime topology revision。
- [Murakkab，OSDI 2026 官方版本](https://www.usenix.org/conference/osdi26/presentation/chaudhry)：§4.4、Figure 10、印刷页 577 / PDF 第 12 页的动态 coding、并行候选、review 和公开测试提前终止。本地旧 arXiv HTML 缺此新增段，不能只据旧稿排重。
- [TOPAS，2608.25523](https://arxiv.org/abs/2608.25523)：在线 prefix-state scheduling；联合 resident prefixes 与 ready requests，未来 ready 时间、ReAct 轮数和未展开工具输出未知。
- [SAGA，2605.00528](https://arxiv.org/abs/2605.00528)：workflow 调度与跨工具状态复用；limitations 明确列出动态图推断、工具尾延迟与新 Agent 时长估计。
- [Nalar，2601.05109](https://arxiv.org/abs/2601.05109)：动态 invocation/future、工作流上下文、局部事件控制与周期全局决策；动态工作流与可修订调度不是空白。
- [Coda，2610.03088](https://arxiv.org/abs/2610.03088)：tiered state admission、compatibility-aware execution admission 与 routing；不是只做 FCFS。
- [CONCUR，2601.22705](https://arxiv.org/abs/2601.22705)：按运行时缓存反馈调整 Agent admission，动态并发不是独立空白。
- [HEAR，2610.06597](https://arxiv.org/abs/2610.06597)：双向语义也容纳依赖、控制、要求与策略，不能说仅交换信息；其附录已有 Harness FIFO prefill gate。
- [Crossflow，2609.27085](https://arxiv.org/abs/2609.27085)：多资源短期 lease 与原子资源协调；TokenCake 的工具边界 KV 调度也已覆盖部分阶段协调。
- [生产 Agent serving 测量，2609.34432](https://arxiv.org/abs/2609.34432)：该平台只观察到很少的兄弟请求服务区间重叠，提醒我们逻辑分支不等于实际宽并发；不能把此平台的比例推广到所有 Harness，也不能从低重叠推断没有逻辑并发或没有调度机会。
- [Throughput-Optimal Scheduling，2504.07347v3](https://arxiv.org/abs/2504.07347v3)：在其排队模型假设下，一类 work-conserving 策略对 DAG/fork-join 也可吞吐最优。不能仅凭 DAG 就宣称原生 batching 吞吐不足；尾延迟、KV/注意力成本与有限资源条件需实测。
- [ODR 固定版本实现](https://github.com/langchain-ai/open_deep_research/blob/1b7d2e80db9faa586165c60e09096dbbfd483a64/src/open_deep_research/deep_researcher.py#L282)：`ConductResearch` 的上限、`asyncio.gather` 和 overflow 错误；源码说明可并行的结构，不能代替实际执行 trace。

旧的 [DSH 生命周期核查](topic1-harness-study-20261028.md) 继续作为实现资料；其截图衍生的八题实验不是当前研究动机或首轮实验。此前 [准入复审](topic1-design-space-review-20261028.md) 的排重仍有效，但“唯一先测固定 READY 调用”不再限制本轮范围。
