Murakkab

Murakkab: Resource-Efficient Agentic Workflow Orchestration in Cloud Platforms

论文：OSDI 2026 | arXiv | PDF

一句话定位

Murakkab 把 Agent workflow 从“开发者硬编码的一串模型和工具调用”改成“声明式任务图 + 用户 SLO + 后端可选执行配置”，再由 optimizer 和 runtime 共同决定模型、硬件和执行方式。它是 application/workflow frontend 与 serving/resource backend 联合设计最完整的代表之一。

它要修正的系统边界

现有 Agent 开发通常跨 LangChain/LangGraph 等编排框架、模型供应商和云资源管理器：应用代码里已经写死模型型号、GPU 类型、并行度、是否启用某工具以及重试方式。结果是三层各自优化局部目标：workflow 层追求功能完成，模型供应层只服务 API，资源层只看实例利用率。后端因此既看不到任务依赖，也无法用“换模型/换硬件/改执行图”来满足质量、延迟、成本和能耗之间的整体约束。

论文的关键判断是：workflow 逻辑相对稳定，执行配置应该是可搜索、可替换、可运行时重配置的变量。 这与只在请求到达后做 batch 排序不同，它把模型与硬件选择本身纳入调度空间。

前后端接口：谁暴露什么

开发者提交的是声明式 workflow：节点是模型、工具或传统 ML 算子，边表示数据/控制依赖；不需要在代码里绑定某一具体模型或 GPU 配置。终端用户提交 SLO，例如最低质量、最大延迟或成本上限。系统维护每个节点可替换的模型/硬件候选和 profile。

因此后端能看到四类信息：

  1. 任务图与可并行/必须等待的关系；
  2. 每个节点可用模型、模型精度和资源形态；
  3. 质量、延迟、成本、能耗等约束；
  4. 集群当前负载与可用资源。

这份 contract 比“传一个 program_id”更强：它允许后端改变执行配置，但不改变应用语义。

系统机制

Murakkab 的生命周期可以拆成三步。

  1. 开发期。 workflow 开发者写逻辑图，平台收集可配置旋钮，例如模型版本、tensor parallel 度、GPU 种类、图像帧数、Agent 数量或轮数。论文用视频问答与代码生成展示配置空间：不同模型和 GPU 组合形成质量、时延、成本、能耗的 Pareto frontier。
  2. 优化期。 profile-guided optimizer 根据离线 profiling 构造满足 SLO 的候选配置，而不是把任意一个局部最快节点当成全局最优。它的任务是删掉显然不满足质量/时延约束的配置，并保留可在不同负载下切换的候选。
  3. 运行期。 adaptive runtime 联合 orchestrator 与 resource manager，按当前负载把 workflow 节点映射到模型和硬件；当资源或请求形态变化时，可改映射而无需改应用代码或重新部署 workflow。

这里的“codesign”不在于某个具体的 cache policy，而在于建立了 workflow specification -> feasible execution configurations -> adaptive mapping 的闭环。

实验应怎样读

论文评估多个 workflow，并把 GPU 使用量、能耗、成本与 SLO 同时作为结果。相对比较对象，Murakkab 最多减少 2.8x GPU 使用、3.7x 能耗、4.3x 成本，同时保持配置给定的质量与延迟要求。这个结果说明：只要前端允许后端替换模型和资源，优化空间比只做 request scheduling 大得多。

不过这些数值应理解为配置/资源效率结果，不是某个 LLM kernel 的通用加速比。复现时要固定：候选模型集合、质量测量方法、SLO、profile 的版本以及负载变化轨迹，否则 Pareto frontier 会变化。

局限与可接入点

  • 论文没有把动态 Agent 分支的在线预测、细粒度 KV eviction、网络数据搬运统一求解；这些需要与 PBKV、TOPAS、Nuska 一类机制组合。
  • profile 的覆盖率决定能否安全重配置；新模型、新硬件或新工具会引入冷启动成本。
  • 它优先适合“workflow 结构可声明、节点配置可替换”的场景；完全黑盒的 ReAct loop 需要先由 Nalar/SAGA 一类接口把结构提取出来。

对项目而言，可以借鉴其 API：把 workflow DAG、node alternatives、quality constraint、deadline/cost budget 作为控制面输入，再让下层 scheduler 决定批处理、KV 与通信细节。
