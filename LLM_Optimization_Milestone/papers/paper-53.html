NALAR: An Agent Serving Framework

Nalar: An Agent Serving Framework

论文：arXiv | PDF

一句话定位

Nalar 的重点是定义 Agent serving 的编程与控制接口：开发者保留普通 Python 的动态性，runtime 则从 futures、state 和 directives 中获得依赖、上下文与资源控制权。

为什么普通 RPC/任务框架不够

Agent workflow 的子任务由模型输出动态产生，包含 LLM、工具、CPU 工作和外部服务；调用可能长时间等待或失败重试。若每次调用只是一次 API/RPC，serving 系统看不到父子关系、后续消费者、可迁移状态或优先级。若要求开发者手写调度和通信，又破坏 Python Agent 框架的易用性。

Nalar 要解决的矛盾是：不限制语言表达能力，但把运行时需要的结构性信息显式化。

前端编程模型

开发者按普通 Python 调用 agent/tool。初始化时可提供可选 directive，例如是否可抢占、是否可 batch、GPU/CPU 最大资源。调用不会立即阻塞，而是返回 future。future 携带调用依赖、上下文、状态引用和完成事件；因此多个 developer agent 可以先被发射，后由某个 aggregation future 等待。

managed state 层将逻辑状态从物理位置剥离。状态不等于某一 worker 内存对象：runtime 可以复用、迁移、重试，并维持一致的恢复语义。这是处理 tool failure、worker preemption 和长生命周期会话的基础。

两级控制面

全局控制层维护系统范围的资源、agent instances、future graph 与策略；可根据排队、SLO、优先级和状态位置决定路由、迁移和资源管理。本地事件驱动层紧贴 worker/agent instance，在 future 创建、完成、失败等事件上快速执行策略，避免所有细粒度事件都同步询问中心控制器。

这种分层避免两种极端：只有全局控制会成为瓶颈；只有本地最短队列策略会看不到跨 agent 的阻塞和状态搬运。论文用“高优先级 future 被长请求堵住”的例子说明：全局层可识别空闲实例，本地层负责把对应 future 迁移过去。

评估说明

论文在三种 Agent workload 上报告 p99 延迟降低 34%–74%、最高 2.9x speedup，在基线失败时维持 80 RPS，并展示约 130K futures 下控制面开销低于 500 ms。这些结果首先证明的是 runtime abstraction 和控制架构的可扩展性；不能直接与只优化单模型 token throughput 的系统做一对一比较。

复现时应记录 future 数量、graph fan-out、状态大小、迁移频率、控制消息、失败/重试比例和不同策略插件，否则很难解释端到端 tail latency。

对 codesign 的启示

Nalar 可直接转化为项目 API 设计：future_id、parent/dependency、context/state handle、preemptable/batchable、resource envelope、deadline/priority。上层不用绑定 vLLM/SGLang；下层可插入 Helium 的图优化、TOPAS 的 KV/关键路径调度或 Strata 的数据面。

它不提供最优具体调度算法，反而是优点：论文解决了“算法能拿到哪些语义、如何执行策略”的系统前提，具体性能仍取决于所接入的 scheduler、KV manager 和状态存储。
