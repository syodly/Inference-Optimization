HEAR: Can Agent Harnesses and Inference Engines Hear Each Other?

一、HEAR

Can Agent Harnesses and Inference Engines Hear Each Other? The HEAR Protocol for Agentic LLM Serving。Jiaqi Zhao、Haodong Chen、Jitai Hao、Wei Zhao、Jinghao Pang、Qiang Huang、Jun Yu，哈尔滨工业大学（深圳）。目前为 arXiv 预印本，原文未标注录用会议；arXiv:2610.06597v1，2026-10-05 提交。论文所列匿名仓库。

问题背景：工作流与推理引擎掌握的信息互不可见

Agent 服务分成两层。Harness 决定执行什么，Engine 决定怎样执行，但高效执行需要同时知道两侧信息。

层次 掌握的信息 缺少的信息
Agent Harness，如 LangGraph、AutoGen、AgentScope 角色分工、请求依赖、工具调用进度、上下文生命周期、未来复用意图 KV 实际驻留、请求队列、资源压力、引擎支持的执行模式
Inference Engine，如 vLLM、SGLang KV 缓存、队列、资源状态、执行模式与成本 请求所属角色、工作流依赖、上下文何时再次使用

三类损失：
误驱逐，引擎不知道某段上下文即将复用，提前释放后只能重新 prefill；
调度失配，harness 不知道哪些请求已有缓存，可能先执行冷请求；
模式错配，不同角色的输入输出与并发特征不同，统一执行配置无法同时适配所有角色。

上半部分是上层知道马上复用，下层却刚驱逐；下半部分是下层已有可用 KV，上层却不知道该先执行谁。HEAR 要解决的是这条信息与控制链路的缺失。

相关工作与核心洞察

相关工作与 insight： AutoGen、AgentScope、LangGraph 管理工作流；vLLM、SGLang、LMCache，以及 H₂O、SnapKV、OmniKV 提供引擎内部的执行与 KV 管理机制；KVFlow、PBKV、Continuum、CONCUR、Pythia 等已经利用工作流或运行时信息做跨层优化。

HEAR 的切入点是这些优化通常依赖特定策略和执行系统，各自定义信号与控制流程，难以移植和组合，耦合性太强。工作流意图与运行时状态具有互补性，但仅交换信息还不够：必须明确消息究竟是描述、偏好、硬约束还是操作结果，否则会把预计复用误当成必须保留，把现在存在误当成资源已预留。

因此，论文的核心贡献是统一双向交互协议，将通信语义与具体优化策略解耦。

系统设计：协议规定语义，策略负责决策

HEAR（Harness–Engine pAiRing）连接现有 harness 与 engine，它定义消息类别、控制效力和操作生命周期；具体怎样调度、怎样保留缓存、怎样选择执行模式，由接入的策略决定。它保持原工作流的任务选择和依赖关系，不修改模型语义。

四类消息构成完整的双向反馈。

方向 消息类别 内容与作用
Harness → Engine 执行描述与意图 角色、阶段、依赖、输入输出规模、上下文生命周期和未来复用预测；提供决策依据
Harness → Engine 执行需求与控制 调度偏好、等待约束、缓存准备／保留／释放请求、执行模式要求；明确希望采取的动作及其约束
Engine → Harness 状态与能力 可复用前缀及存储层、队列、容量压力、支持的操作和配置、执行成本；返回当前观测
Engine → Harness 执行结果 接受、完成、拒绝、不支持或失败，实际配置、回退、缓存复用、延迟与错误；确认实际发生了什么

左侧是四类消息，右侧是多个 agent 在生成、工具调用和结束之间切换时的交互。蓝色传递工作流信息与控制，橙色返回引擎状态与结果；

通用决策形式为：

di = π(hi, sj)

其中，hi 是当前工作流信息，sj 是引擎最新反馈，π 是具体策略，di 是输出的执行决策。两侧更新可以异步发生，因此不能假定状态报告与决策时刻完全同步。下面两类实例用同一套契约，分别处理在线调度和角色级配置。

实例一：缓存感知运行时协同及实验

Cache-Aware 根据引擎反馈，从请求开头逐块查找连续可复用前缀，并分别统计 GPU、CPU 层的命中。覆盖提示词至少 50% 的请求判为 hot，其余为 cold；cold 保持默认优先级，hot 按 priority 排序，可复用块越多越先执行。调度时看到的缓存可能随后被驱逐，实际执行前引擎仍需重新核验。

Guard 给这种命中优先策略加等待约束：请求等待超过 W 秒后进入受保护优先级，后续热请求不能再绕过或抢占它，受保护请求按等待先后执行。

Session-Aware 独立控制驱逐顺序：harness 根据已完成会话的返回行为估计继续概率 p，引擎结合闲置时间计算保留优先级 r = p·exp(−idle/400)。越可能继续、越近期访问的上下文越优先保留。

三者分别解决及时使用已有缓存、限制冷请求等待、让缓存留到下一轮，可以组合。这里仍是连续前缀复用，遇到首个缺失块便停止；HEAR 没有让其后的驻留块独立参与复用，也没有引入 CacheBlend 式修复。决策随缓存事件与调度点在线更新。

负载与设置。 SCBench（面向长上下文推理的 KV 缓存评测基准） Mooncake ；从同一 15 分钟内开始的会话中回放 50%／75%／100%，保留完整轮序和时间间隔。两者使用 Qwen3-8B，分别部署在单张 RTX PRO 6000、单张 H100，均配置 96 GiB L2 KV 缓存。基线为引擎默认 FCFS，各组模型、负载与缓存容量一致。

Cache-Aware 将复用率从 19.2% 提升至 87.6%，全部会话完成时间从 481 秒降至 224 秒，但最大 TTFT 从 79.0 秒升至 93.9 秒，说明热请求优先会牺牲冷请求等待。

加入 Guard-40 后，完成时间为 299 秒，整体加速 1.61 倍；中位 TTFT 从 63.1 秒降至 28.3 秒，改善 2.23 倍；P95 从 74.2 秒降至 51.1 秒，改善 1.45 倍；复用率为 66.1%。核心结果是复用收益与等待约束的折中，并非命中率越高越好。

50% 负载下主要损失来自闲置期间驱逐，Session-Aware 将复用率从 19.5% 提升至 31.9%；75% 负载下，会话保留与缓存感知调度组合获得最短会话等待、最高吞吐和最高复用；100% 负载下，Cache-Aware 在中位 TTFT、会话等待与吞吐上更有优势，Session-Aware 则改善尾延迟和复用率。最优策略取决于负载及优化指标，完整组合不总是最优。

实例二：能力感知执行配置及实验

harness 提供角色、工作阶段、负载规模、优化目标和质量要求；引擎提供各模式的实测延迟、吞吐、KV 容量与稳定性。

作者测试 Main {vLLM, OmniKV} × Reader／子 agent {vLLM, H₂O, SnapKV} 六种组合，先按质量和稳定性筛选，再以完成时间选择角色—模式映射。映射在正式实验前冻结，在工作流初始化时加载。

负载与设置。 BrowseComp-Plus 每组 208 道检索问答，DeepResearchBench 每组 100 个深度研究任务；共同采用 LangGraph 的 Main–Retriever–Reader／子 agent 编排，保留各自检索环境。Main 与 Reader 均使用 GLM-4.7-Flash，部署在独立 H100 上；比较上述六种配置，任务和工具预算一致。

BrowseComp-Plus 选择 vLLM／H₂O，总时间从 5.69 小时降至 4.62 小时，加速 1.23 倍，Judge accuracy 为 46.63%，基线为 46.15%；DeepResearchBench 选择 OmniKV／H₂O，完成时间从 5.93 小时降至 2.42 小时，加速 2.45 倍，RACE 为 41.1%，基线为 40.6%。

主要收益来自 Reader／子 agent 切换到 H₂O，平均延迟分别降低 5.60 倍、7.22 倍。BrowseComp-Plus 同时减少 76.2% 的 prefill token，复用率从 6.2% 升至 80.3%。

Main 的选择随负载变化：约 0.4K 输出的 BrowseComp-Plus 更适合 vLLM，约 4.4K 输出的 DeepResearchBench 更适合 OmniKV。强行统一使用 OmniKV／H₂O，会使前者比所选配置慢 7.8%；统一使用 vLLM／H₂O，会使后者慢 14.0%。

论文证明的是统一协议能够承接不同优化策略，并让工作流意图与实时状态共同参与决策。 收益包含接入的缓存与执行模式，不能全归于协议本身。
