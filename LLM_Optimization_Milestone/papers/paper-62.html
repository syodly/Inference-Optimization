TokenRouter: Efficient Serving System for Token-Level LLM Routing

二、TokenRouter

TokenRouter: Efficient Serving System for Token-Level LLM Routing。Tianyu Fu、Tengxuan Liu 等，清华大学、卡内基梅隆大学。NeurIPS 2026；arXiv:2610.12242v1，2026-10-08 提交。代码。

解决问题

场景是 同一段回答的生成过程中，按 token 或短片段切换大小模型或不同专家模型。简单位置交给小模型，困难位置调用大模型，再返回继续生成；不同于每次请求只选择一个模型，也不同于固定的 speculative decoding 。

相关工作与 insight： R2R、CITER 等算法利用生成难度的变化减少大模型调用，但标准 serving 系统主要按单模型持续生成组织执行，无法自然承接频繁的模型切换。

少调用大模型不一定带来更快的服务，同步等待、零散入批和重复 KV 管理可能吞掉计算收益。

TokenRouter 将路由逻辑与模型执行解耦，让请求切换时保留各模型已有状态，并按模型重新组批；

左图从 session、query 到 token 逐步细化路由粒度；右图为每个模型设置独立 subserver。token 级决策把算法收益转化为三类系统开销：同步执行时小模型必须等大模型；异步执行时切换请求到达不规则，容易错过当前 batch；每次返回若被当作新请求，还会反复做前缀匹配和 KV 管理。 路由算法同时与连续 batching、缓存和调度耦合，开发者难以直接接入标准 serving 系统。

解决方案

按请求描述算法，按模型组织执行。设计 route / send / receive 接口指定何时切换、传递什么状态、如何接收结果；

1、避免跨模型逐步同步，如果要跨模型再同步时间消耗大，取消同步屏障，自己做自己的。

请求离开本模型时标为 pending，保留其服务与 KV 状态；返回时追加对端生成的 tokens 并恢复执行，减少重复前缀匹配和 KV 分配。

2、模型立即异步执行会产生零散 batch。

TokenRouter 对大模型到达请求先缓冲，达到阈值再组批，摊薄执行与入批开销。

阈值由并发数、路由概率和模型单步延迟构成的吞吐模型选择；

实验数据集、场景与效果

workload 数据与输入输出规模
Low-effort reasoning AIME2024，输入约 100 tokens，最大输出 2,048
High-effort reasoning AIME2024 中较长推理题，最大输出 8,192
Agentic tasks SWE-Smith 多轮轨迹，输入约 8,192，最大输出 1,024

测试平台为 8 张 A100 80 GB 的服务器。主要双模型比较使用 Qwen3-0.6B、Qwen3-32B，通过 CUDA MPS 共用两张 GPU，小模型 TP1、大模型 TP2；三模型 ME 使用 0.6B、8B、32B。支持 CITER、R2R、R-Stitch、Co-LLM、ME 五种路由算法,路由调度策略非创新，也在原算法的模型与数据配置上补充测试。

基线包括算法官方实现，以及作者构建的 Std. Serving：每个模型部署标准 SGLang server，外部 dispatcher 逐 token 路由。

三个 workload、五个路由算法的 15 种组合中，相对较强基线，吞吐提高 2.01–64.15 倍；相对 Std. Serving，请求完成延迟降低 2.03–63.64 倍。纵轴吞吐是生成 token/s，延迟是请求完成时

消融显示收益包含 CUDA Graph、异步执行和延迟组批。R2R、并发 8 下，基础实现约 132.8 token/s，扩展 Graph 后 230.8，加异步执行后 296.9，加延迟组批后 372.5。TokenRouter 的重点是把已有 token 路由算法高效部署。
