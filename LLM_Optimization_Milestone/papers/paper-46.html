精读笔记

Akashic: A Low-Overhead LLM Inference Service with MemAttention

二、Akashic

Akashic: A Low-Overhead LLM Inference Service with MemAttention。Yang Liu 等，小红书、上海交通大学、北京大学。arXiv:2607.05708v1，2026-07-07 提交。

解决问题

场景是长期对话和多步骤 Agent 不断积累历史：多轮交互、工具调用和跨会话工作流会把上下文持续推长。每轮携带完整历史会增加 prefill、超过模型窗口，并把真正相关的证据埋在无关内容中；即使模型支持很长上下文，读取和处理这些 token 仍然昂贵。

现有记忆方案有两种的风险。
整段总结 需要反复处理越来越长的历史，更新成本随历史规模增长，而且不同主题容易混在同一个 memory object 中，带来噪音。

独立按段 总结虽然把单次维护成本限制住，却可能把一个事实或事件拆到多个段里，后续检索只取到其中一段，丢失跨段依赖。同时分散的存储也会带来存储检索和 IO 的问题

图 2 展示了为什么不能对所有历史采用固定的压缩比例。不同数据集的数据密度不一样，左图中，LoCoMo 对话有较多可压缩内容，而 SWE-bench 软件工程轨迹需要保留的内容明显更多；右图中，BrowseComp 和 WebArena 在同一条任务轨迹的不同阶段，保留比例也会波动。

图 3 展示另一个问题：输入变短，不代表整个流程一定更快。灰色柱是常规推理，黄色柱是加入记忆处理后的推理；在 SWE-bench、BrowseComp 和 WebArena 场景下（压缩比很高的任务），黄色柱明显更低。原因是生成、更新和使用记忆本身也需要处理，可能抵消缩短上下文节省的计算。说明现有记忆流程开销的动机实验。

存储层的gap：语义上经常一起检索的记忆块，可能因为生成时间不同而散落在不同磁盘页或 block 中。

一次 cross-chunk 推理即使只需要少数记忆，也可能触发多次分散读取，增加 I/O、读放大和并发下的检索延迟。

解决方案

MemAttention 增量记忆 + 关联放置：
默认按 1024 tokens 分块，达到阈值后压缩当前块；
模型从旧记忆元数据中选择 top-5 语义相关块进行联合更新（joint compact），修正或删除过时信息。（块交叉信息恢复，更新）

回答时再按 query 选择top-5语义匹配的块，按时间排列并加入 prompt。
存储侧将关联块 (上面联合更新的)共置，采用异地写入和垃圾回收减少读取碎片。

图 5：分块压缩、跨块推理、物理整理与记忆检索构成整体流程。

实验数据集、场景与效果

论文覆盖四类 workload，质量指标随任务不同而变化：

数据集 场景 质量指标
LoCoMo 长期多会话对话记忆与问答 QA F1
SWE-bench 信息密度较高的软件工程轨迹 问题解决率（%Resolved）
BrowseComp 网页检索与浏览推理 Accuracy
WebArena 多步骤网页交互任务 任务成功率

使用 Qwen-8B、OPT-30B、Llama-70B：8B/30B 配 1 张 H800 80 GB，70B 配 2 张 H800，服务器配 4 TB NVMe SSD。单请求质量/吞吐图覆盖 LoCoMo、SWE-bench、BrowseComp；并发请求率实验覆盖 LoCoMo、SWE-bench、WebArena，不能把每张图都当作四数据集全覆盖。（表 1、§5.1–5.3）

LoCoMo/BrowseComp 上，相对 MemGAS，正文报告吞吐约 1.10–1.21 倍、质量提高 4.2–7.2 个百分点。SWE-bench 上，相对 Full-context 的吞吐只有 90.5%–91.8%，但解决率提高 0.6–1.1 个百分点，记忆维护并非在所有场景都比直接输入全文更快（对应insight）。

并发实验中，SWE-bench 相对 Mem0 可持续请求率约 1.53–1.88 倍，领先所有baseline。

存储实验 基线 Append-only，Semantic-only，Akashic
LoCoMo 相对 Append-only，每请求读取块数由 6.8 降为 3.4，冷缓存 p95 检索延迟由 38 ms 降为 22 ms。
