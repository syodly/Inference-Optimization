前端派发改变的，
不止当前队列

研究 Harness 如何结合推理引擎状态，决定 DAG 何时展开、当前工作如何分波派发。先从任务推进与资源代价的冲突寻找痛点，再用真实执行验证；不限于某个 Harness 的实例生命周期。

主线：动态 DAG 的展开与派发实现载体 ≠ 研究边界研究假设 · 尚无实测收益或新颖性结论

要优化的到底是什么？

任务语义决定一次执行的价值，引擎状态决定它的代价；而这次执行，又会改变后续负载。

目标是让用户更早得到有效的最终结果，并在相同质量与资源下完成更多任务。可见队列变短、单次调用变快，都不足以单独证明成功。

Harness 知道：接下来可能发生什么

已揭示依赖、结果如何汇合、哪些分支尚未启动、哪些工作正在等工具、哪些探索允许省略。未来的完整图和准确工具输出通常未知。

Engine 知道：现在做它实际有多贵

模型队列、实际 KV 驻留与命中、额外 prefill、batch 干扰、可分配容量。空闲显存和请求数无法独立代表完整执行成本。

Harness → Engine · 任务与工作信息依赖、当前合法调用、已知展开规则、工具中工作与不确定性。
Engine → Harness · 执行成本与状态反馈真实队列、容量与缓存情况、接受或失败结果；由引擎最终核验容量。

Workflow 定义哪些工作合法、什么算完成；Harness 负责把它推进成具体调用；Engine 决定资源如何执行。协同可以跨这三层，不能都叫“调整 Agent 数”。

同样完成一个请求，后续可能完全不同

下面是三种行为示意，不是某个已运行工作流，也不是性能数据。箭头都表示明确的依赖或阶段推进。

01让任务收敛

最后一个必做分支完成
允许汇总↓
生成最终结果

这一段进度可以转化为用户完成时间。是否优先，仍需考虑冷 prefill 和资源干扰。

02释放后继工作

规划节点完成
揭示合法分支↓
多个研究／候选分支

本次请求可能很短，却释放了大量工作。下一波何时开始，是可检验的控制点。

03暂时离开模型队列

模型发出工具调用
工具执行并返回↓
形成下一次模型调用

队列暂时下降，已经启动的任务仍可能在随后形成负载。在线不知道准确返回时刻。

四类痛点：展开查看信号、动作与已有覆盖

它们是机会审计的分类，不是四项已确认创新。优先检验第二类，再决定是否需要第三类的质量闭环。

基础矛盾 · 强基线① 请求执行得更多，用户任务却迟迟不结束

直觉：一根任务只差最后一个分支，另一根刚要铺开大量工作。只追命中率或 batching，可能让每根都在推进、却没有最终结果；只追关键路径，又可能付出大量缓存搬运和冷 prefill。

信号与动作：依赖、join、剩余进度 × 实际 KV 与执行成本；选具体 READY 调用、分波或路由。ALL join 不要求所有分支同时启动。

已有覆盖：TOPAS 已联合前缀驻留、请求准入与最长剩余路径；SAGA、TokenCake、Coda 也有相邻机制。此项应构成基线，单独做优先级分数的创新空间较窄。

优先审计 · E1② 当前不堵，已经在途的工作却会制造下一轮拥塞

直觉：相近的队列和 KV 状态，一次背后有许多研究分支等搜索结果，另一次没有。相同的“再放一批”动作可能产生不同后果。也不能一直压住新工作，否则 GPU 和工具流水线会空等。

前端可提供：工具中工作、已等待时长、已知后继规则、当前只显露了一部分的图。只能用历史分布估计回流，不能偷看未来工具返回或完整子树。

可操作动作：必做分支分波启动；选择下一轮规划与汇总的顺序；放行或暂缓已经绑定输入的模型调用。必做工作不删，工具只在启动前且语义允许时延后。

已有覆盖与待测差异：Nalar 已支持动态工作流和可修订调度，SAGA 已讨论动态图与工具长尾。需对照简单背压、固定分波和工作流感知调度，证明“未提交的工作＋展开控制”仍带来独立价值。

先验证两件事：这些信息是否解释真实损失；得到同样信息的后端调度器能否解决。位置在前端本身不构成创新。
有条件扩展 · E2③ 立即多做一些，还是等部分结果后再决定？

直觉：允许多个代码候选时，先做少量、失败后再展开可以省工作；全部并行可能更快。取舍同时受有效验证信号和当前共享引擎代价影响。

动作边界：只控制应用声明可选的候选、review 或迭代；用公开测试等在线信号，最终质量独立离线评估。它改变工作集，必须与固定工作量调度分开报告。

已有覆盖：INFRAMIND 已做资源感知初始拓扑、Agent 数与逐步路由，也列出运行中拓扑修订；Murakkab OSDI 2026 §4.4 已包含动态 coding、候选数量、review、公开测试驱动的提前终止。

潜在问题是共享引擎的边际成本如何与部分有效结果联合决定扩展；单纯“高负载少开几个 Agent”与已有工作重合较多。ODR 第一阶段不凭主观判断删 researcher。
鲁棒性检验 · 暂不单独立题④ 每个 Harness 都在响应，整个系统却一起过度响应

直觉：多个 Harness 同时看见空闲、同时展开，之后又同时退让。平均并发不高，仍可能发生拥塞、长尾与不公平。

动作与约束：共享准入、老任务进度保护、反馈过期处理与有限放行。引擎保留最终容量仲裁权；快照不等于资源预留，不默认发明整组承诺或两阶段协议。

已有覆盖：CONCUR 的反馈式 Agent admission、Crossflow 的多资源 lease、Nalar 的局部与全局控制均是近邻。将多 root、反馈延迟和工具长尾纳入 E1，而不据此另起一条研究线。

最关键的反问：后端拿到同样信息，能不能做？

仅改变已就绪请求的顺序

如果工作与 prompt 都已确定，前端排队通常能被有相同 DAG 信息的后端策略替代。必须比较同信息的工作流感知后端，防止把排队从一层搬到另一层。

改变请求形成之前的工作

在分支触发工具之前选择启动时机；利用部分结果决定是否展开可选工作；暴露动态生成图的已知规则。这些动作需要 Harness 语义或回调，也是更值得检验的控制空间。

即使动作发生在 Harness，也可能由后端通过回调发起。比较相同信息、相同动作权限后，剩下的机制收益才有说服力。新的协议名字或代码位置不足以形成贡献。

先做两个实验，回答不同的问题

E1 · 必做工作固定

看见当前请求之外的工作，有没有价值？

首选载体：ODR 的 supervisor → researchers → 搜索／阅读 → 汇总；先量实际并发与工具中工作。递归研究和窄前沿条件检索作边界。

动作：分波启动已获准分支、暂缓／提交合法调用。固定必做工作与原始配置，不靠减任务获益。

对照：原生调度 → 引擎压力 → DAG＋缓存 → 在途工作与简单背压 → 联合展开；再加同信息、同动作权限的后端对照。

结果：用户提交到有效最终结果的 P50/P95、按时完成任务数、两层等待总和、实际 KV／prefill、工具延迟、公平性和控制开销。

E2 · 工作量允许变化

部分结果与实际资源代价，是否应该共同决定扩展？

条件：应用有可选工作与有效在线验证，例如代码公开测试；隐藏测试仅离线评分。

动作：下一候选何时启动、失败后是否继续、可选 review／迭代；必做工作不受影响。

对照：全部并行、串行失败再展开、固定波次、压力策略、质量反馈，以及 Murakkab／INFRAMIND 相关机制组合。

结果：质量—任务耗时—实际成本曲线，及给其他任务带来的收益。不能只报少生成几个 token。

实验可信度：必须防止哪些假收益？

不转移排队：计时从用户任务提交开始，包括前端等待。不能只看 Engine queue 或 TTFT。

不偷看未来：在线使用已揭示图、工具已等待时长与历史分布；准确返回时间只可用于标明的上界对照。

不固定错误到达时间：回放按依赖与相对工具时长推进；修改派发以后，原始绝对请求到达时间不再有效。录制 prompt/结果回放只能诊断系统效应，后续仍需真实闭环。

不偷换 ODR 配置：原生并发配置还会进入规划 prompt，超出的调用会收到错误。固定原配置，在已获准工作外加分波，避免把任务删减当调度收益。

不假定宽并发：生产研究曾观察到很少的兄弟请求执行重叠；先测目标 workload。若前沿长期只有一个节点，就检查阶段衔接，不编造宽 fan-out 动机。

第一阶段是机会审计，尚未接入真实引擎。具体信号、动作、比较组、消融与继续条件见 完整实验方案。
