# 初始实验协议

## 要检验的三个具体问题

1. **质量与分解**：同一模型读取全部文档和将文档交给子 Session 后汇合，是否得到相近的有效回答？先比较校准集 EM/F1、支持文档保留和长度截断。若证据压缩丢失信息，先修任务流程，不把质量下降包装为提速。该比较工作量不同，只是应用校准。
2. **展开与收敛竞争**：相同必做节点下，直接释放全部 READY 调用是否使接近完成的父任务被新分支干扰？比较静态 cap 扫描、同 cap 的 FCFS/进度优先、实际后端优先级，测整任务平均/P95 时延、完成曲线、吞吐和公平性。若最优静态 cap 已解决问题，必须如实承认。
3. **在途工具的未来需求**：引擎当前队列与占用相近时，在途工具的数量、阶段和已等待时间，是否能解释接下来几秒的请求峰值与完成损失？先做自然工具对照，再做明确标注的返回延迟控制。不能把“工具更多”本身当作有用信息，必须证明它在已有引擎状态之上提供预测或决策收益。

## 轮次与对照

- 每轮 8–24 个完整根任务，保存失败和长尾，目标数分钟，不以十五分钟切掉数据。实验顺序交叉；评估集不用于手动改 prompt。
- 同一服务进程、权重、GPU、参数；首次编译/预热独立。每轮在引擎空闲后调用真实缓存复位接口，核查 success，再开始到达计时。后续单独做自然热缓存对照。
- E1 只改派发时机和顺序。分支、模型预算、文档、工具、采样 seed 和到达计划保持一致；浮点批处理可能导致输出与 token 变化，须报告、必要时增加固定调用 trace 回放以区分因果。
- 第一组静态 cap 至少含 4、8、12、24 和直接派发；自适应策略不能只挑一个差 cap 作对手。进度优先有老化，需报告后来任务是否饥饿。
- `pressure` 只使用实际 Prometheus 指标；计数器差值跨轮取首尾，记录可观测性和采样误差。缓存占用低或零抢占也是有效负结果。
- 机制设计在实测损失之后。先与简单分波和背压比较，再给后端相同依赖/工具信息；后端只支持优先级而无法撤回或延迟展开时，需要明确其动作集不同，不能声称等价比较。

## 证据强度

初轮小样本用于发现与排错，不直接支撑顶会级结论。后续用配对任务、多次顺序重复和区间估计确认稳定性。报告有效质量、总工作量、失败、整任务时延、API 首 token 时间、前端等待、工具回流、真实引擎等待和缓存占用；单看 GPU 利用率或某次平均时延不构成痛点证据。

## 模型能力和 DAG

E1 固定同一权重和非思考模式。独立 E2 比较思考模式、证据预算及经应用允许的自适应分支/修复。模型能力会影响规划准确性、必要分支数量与失败修复，不能把减少质量要求的结果归因于调度。后续动态图须由真实可见的工具结果与模型决策驱动，隐藏答案仅用于离线判断。
