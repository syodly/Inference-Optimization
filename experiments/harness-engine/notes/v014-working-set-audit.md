# v014 工作集机制的初步对照

本批在同一个双卡图模式服务上固定八道长文题、三个子Session、每题十次必做调用，比较七种派发设置并保留原生重复。两次直接派发均值169.41/171.21秒，均无evidence命中，分别抢占22/12次；固定模型调用上限12消除抢占却耗时181.49秒、仍无命中。回流优先12为166.64秒、命中44.8%。跨工具计账的Session窗口12为157.15秒，但P95恶化到207.95秒；窗口18为151.35秒、P95为183.07秒、命中32.2%。同为十八的调用上限为162.84秒、零命中；后端阶段优先为168.72秒、零命中。窗口18答对5/8，输出49176 token，与首轮48930接近；原生重复与回流优先答对6/8，不能忽略质量变化。结论暂限于工作集形状值得研究，未证明稳定加速或新颖性；v015正在固定80份输入和48930个解码token重新执行真实引擎以做归因。

## 可复现材料

- 远端所有 `runs/v014-*` 保存完整prompt、工具结果、事件、指标和源代码快照；本地 `results/v014-*` 保存摘要及一个完整根任务。
- 配置 `configs/session-window-v014.json`；汇总 `results/v014-comparison.json`；图与数据 `results/figures-v014/`。
- 当前同信息后端基线只提供阶段优先级，尚不具有Session窗口的同等展开权限，不能以它输掉实验就宣称前端位置独有优势。
- 精确token前缀审计发现 `/tokenize` 没有像Chat接口一样将历史 `reasoning_content` 标准化为 `reasoning`；已修正审计工具，旧版 `all_token_counts_match_usage=false` 的长文审计不得用于精确前缀归因。真实usage缓存计数和上述耗时不受这项审计工具错误影响，待计时批次之间重跑。
