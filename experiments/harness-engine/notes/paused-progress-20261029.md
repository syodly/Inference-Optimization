## 我们究竟在研究什么

研究的是：**Harness 在向共享推理引擎提交请求之前，能否利用任务依赖、持久 Session 和实际引擎状态，决定哪些工作现在启动、哪些回流请求先提交，从而让完整任务更快完成。** 计时从用户任务提交开始，包含前端等待、模型推理、工具执行和最终汇合。文中的“任务耗时”即这个时间，不需要先理解 JCT 缩写。

当前 E1 固定全部必做工作，改变派发时机与顺序，避免把少做工作算成调度收益。E2 单独研究可选 Agent 是否值得增加，以及推理模式是否改变它的价值；目前尚未进行 GPU 实测。

## 目前效果：痛点成立，创新收益尚未成立

### 1. 固定工作量下，长短任务确实严重相互干扰

v021 的混合回放每轮固定 160 份输入和 66,893 个实际解码 token。**同样的短任务单独运行平均 34.89 秒，混入长任务后为 138.43–140.50 秒，约四倍。** 长任务也由独占 170.90 秒变为 196.55–198.62 秒。这是目前比较扎实的系统痛点证据；但它本身还不能证明必须由前端联合后端状态解决。

### 2. 复杂历史预算暂时没有超越普通回流优先

同一 v021 固定工作量对照中，普通回流优先、在途上限 24 的均值 **138.17 秒**；历史预算为 **137.58 秒**，只相差约 **0.43%**。预算方案 P95 为 **212.47 秒**，反而高于普通回流的 **206.33 秒**。因此不能宣称“历史计账机制已经带来独立收益”。短请求优先能降低均值，却会让长任务更慢，说明均值与公平性需要一起看。

### 3. 两个独立 Harness 共享引擎，完整闭环出现了改善候选

v024 已完成八轮。目标 Harness 处理 16 题，背景 Harness 另做 4 道长文题，两边都完成真实有用工作。目标控制器只能看自己的图和全局引擎指标，不能看背景 DAG 或未来到达。

- 目标独占平均 **145.76 秒**；加入背景后直接提交的两轮为 **236.34 / 227.41 秒**。
- 普通回流优先为 **218.27 秒**；Session 窗口加相同回流排序为 **196.49 秒**。
- 历史预算为 **200.38 秒**，再加压力反馈为 **201.48 秒**，没有超过上述简单 Session 窗口组合。
- 窗口方案的背景平均 **216.82 秒**，低于直接提交两轮的 **257.39 / 269.45 秒**；目前没有看到通过拖慢背景换取目标改善。

**这些是完整闭环观察，不是固定工作量加速结论。** 各轮生成 token、长文答题准确率会变化；窗口方案目标长文为 6/8、短文 F1 为 0.792，背景只有 1/4 正确。背景样本少、质量低且各策略仅少量重复，尚不足以声称普遍有效。完整八轮表和原始路径见 [v024 结果](v024-shared-outcome.md)。

### 4. “工具回流导致缓存损失”的解释已收窄

长文实验确实观察到低缓存复用和抢占，但 v019 对自然工具的逐 Session 审计显示工具后平均间隔只有约 9 毫秒，间隔内没有新冷 draft 提交。因此不能把已有损失一概归因为长工具等待期间被新任务挤出。v020 另加明确标注的 12±3 秒工具等待作为干预，不能冒充真实生产工具耗时。命中率提高也没有必然转化为更好长尾。

## 当前判断

目前最有根据的研究问题是：**多个 Harness 共享引擎时，如何控制新的持久 Session 启动与既有 Session 回流，使完整任务推进更好，同时不伤害其他任务。** 已有证据支持干扰存在，但还没有证据说明后端压力信号比简单窗口与回流排序提供稳定额外价值。动态改变 Agent 数量的质量价值也尚未测到。

因此当前成果是可复现的真实实验系统、一个明确痛点，以及淘汰若干过强机制解释的负结果；**还不是已经做出可支撑论文结论的独立调度机制。** 如果将来恢复，先补完 v025 因果对照，再看 v026 信息/动作权限对照与 v027 质量价值，避免直接继续堆复杂算法。暂停期间不自动推进这些工作。
