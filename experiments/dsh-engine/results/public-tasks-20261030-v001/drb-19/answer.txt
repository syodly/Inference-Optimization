

# Prometheus 高流失率（High Series Churn）的影响与系统性解决方案

## 一、什么是"高流失率"

在 Prometheus 语境下，**高流失率（High Series Churn）** 指的是时间序列（time series）的创建和消亡速率很高——即活跃序列集合在持续快速变化。它与"高基数（High Cardinality）"相关但不同：

| 概念 | 含义 |
|------|------|
| **高基数** | 同一时刻活跃序列总数很大 |
| **高流失率** | 序列集合变化速率快（新序列不断出现、旧序列不断消失） |

典型场景：Kubernetes 中 Pod 频繁重建、微服务实例频繁扩缩容、按用户/请求 ID 打标签、临时 Job 频繁执行等。

---

## 二、高流失率造成的影响

### 1. 内存压力（最核心问题）
- Prometheus 的 TSDB 将**活跃序列**（head 中的序列）全部保存在内存中
- 每个活跃序列占用约 **1–2 KB** 内存（label pairs + chunk head + 元数据）
- 高流失率意味着任意时刻都有大量"半活跃"序列驻留内存
- 直接后果：**OOM（Out of Memory）**，Prometheus 进程被 kill

### 2. Compaction 开销激增
- 序列从 head 写入后，需要 compaction 到磁盘 block
- 高流失率 → 大量短命序列 → 产生大量小 block → compaction 任务堆积
- 后果：**磁盘 I/O 飙升**、CPU 占用升高、compaction 延迟增大

### 3. WAL（Write-Ahead Log）膨胀
- 高写入速率 + 高序列数 → WAL 文件快速增长
- 后果：磁盘空间压力、重启恢复时间变长

### 4. 查询性能下降
- 查询时需要扫描 head 中的所有活跃序列
- 序列数越多，`/api/v1/series`、`/api/v1/label/.../values` 等元数据 API 越慢
- 后果：**查询延迟增大**、`/metrics` 页面变慢

### 5. Remote Write 压力
- 如果配置了 remote write，高流失率意味着需要追踪和发送的序列元数据更多
- 后果：remote write 队列堆积、数据丢失风险

### 6. HA / 副本同步压力
- 如果使用 Prometheus HA 模式，高流失率意味着两个副本之间的状态同步开销更大

## 三、系统性解决方案

### 第一层：源头治理（最重要）

#### 1. 标签卫生（Label Hygiene）
- **避免高基数标签**：不要在指标中使用 `user_id`、`request_id`、`trace_id`、`url_path`（含参数）等
- **使用 `metric_relabel_configs` 在采集端丢弃/替换高基数标签**：
  ```yaml
  scrape_configs:
    - job_name: my-service
      metric_relabel_configs:
        - source_labels: [user_id]
          action: drop          # 直接丢弃含 user_id 的序列
        - source_labels: [url_path]
          regex: '.*'
          target_label: url_path
          replacement: 'other'  # 归一化
  ```
- **使用 `labeldrop` / `labelkeep`** 在 remote write 端过滤

#### 2. 预聚合（Recording Rules）
- 用 recording rules 将高基数指标预聚合为低基数指标
- 例：`sum by (service) (http_requests_total{user_id=~".*"})` → 只保留 service 维度
- 查询时查预聚合结果，避免实时扫描大量序列

#### 3. 指标设计审查
- 建立指标命名和标签规范
- 使用 `promtool check metrics` 等工具审查
- 在 CI/CD 中加入基数检查（如 `promtool tsdb dump` 分析）

### 第二层：Prometheus 自身调优

#### 1. 启用 `memory-series` 特性（Prometheus 2.38+）
```bash
--enable-feature=memory-series
```
- 将不活跃序列从内存中卸载，显著降低内存占用
- 对高流失率场景效果明显

#### 2. 启用 `tsdb-allow-myriads` 特性（Prometheus 2.53+）
```bash
--enable-feature=tsdb-allow-myriads
```
- 允许 TSDB 处理数百万级序列
- 内部优化了序列索引结构

#### 3. 启用 `delayed-compaction` 特性（Prometheus 2.53+）
```bash
--enable-feature=delayed-compaction
```
- 延迟 compaction，减少 I/O 峰值
- 适合高写入、高流失率场景

#### 4. 启用 `o-lazy-loading` 特性（Prometheus 2.53+）
```bash
--enable-feature=o-lazy-loading
```
- 延迟加载 block，减少启动和查询时的内存峰值

#### 5. 调优 TSDB 参数
```bash
--tsdb.retention.time=15d          # 缩短保留时间
--head-chunks=2000000              # 调整 head chunk 数量
--tsdb.max-block-chunks=10000000   # 限制 block 中 chunk 数量
--no-lockfile                      # 减少文件锁开销
```

#### 6. 启用 `auto-gomemlimit`（Prometheus 2.45+）
```bash
--enable-feature=auto-gomemlimit
```
- 自动设置 Go 运行时内存限制，避免 OOM

### 第三层：架构层面

#### 1. 使用 OpenTelemetry Collector 做中间层
- 在 Prometheus 和采集端之间插入 OTel Collector
- 利用 Collector 的 `metricstransform`、`filter` 等 processor 做标签过滤和聚合
- 解耦采集和存储，便于独立扩展

#### 2. 使用更强大的时序数据库
- **VictoriaMetrics**：对高基数场景优化更好，内存占用更低
- **M3DB**：专为高基数设计
- **InfluxDB**：TSM 引擎对高写入优化好
- **Cortex / Thanos / Mimir**：分布式 Prometheus，支持水平扩展

#### 3. 分片（Sharding）
- 按 namespace / service / 业务线分片
- 每个 Prometheus 实例只负责一部分序列
- 配合 Thanos / Cortex 做全局查询

## 五、总结与建议

### 解决优先级

```
1. 源头治理（标签卫生 + 预聚合）     ← 最重要，效果最显著
2. Prometheus 特性调优（memory-series 等）
3. 架构升级（OTel Collector / 分布式 TSDB）
4. 云厂商托管服务（如果已在云上）
```

### 核心原则

> **高流失率的根本解法是减少序列数量，而不是增加存储容量。**

- 每减少一个高基数标签，可能减少 **10x–1000x** 的序列数
- 云厂商托管服务的核心价值在于：**自动扩缩 + 内置基数管理 + 标签过滤**，让你不需要手动调优 Prometheus 参数

### 快速行动清单

1. ✅ 用 `promtool tsdb dump` 或云厂商的 Cardinality Dashboard 找出 Top N 高基数指标
2. ✅ 审查这些指标的标签，识别高基数标签
3. ✅ 用 `metric_relabel_configs` 在采集端丢弃/归一化高基数标签
4. ✅ 用 recording rules 预聚合关键指标
5. ✅ 启用 `memory-series`、`tsdb-allow-myriads` 等 Prometheus 特性
6. ✅ 如果已在云上，考虑迁移到云厂商托管 Prometheus 服务
