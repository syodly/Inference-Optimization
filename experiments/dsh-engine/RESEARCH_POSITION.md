# DSH 是实验载体，研究贡献必须另证

## 先纠正之前的身份描述

官方DSH源码和MIT许可证可获取。此前“我们没有完整源码”的表述不准确；旧实验确实没有运行官方DSH，其Python实现只能称自建受控Harness。旧数据不改写成DSH测量，新部署单独编号、配置与存储。

## 已有能力与候选研究的区别

| 层次 | 官方DSH已有职责 | 本研究是否需要重做 |
|---|---|---|
| 执行正确性 | 创建/继续/取消Agent，管理持久Session、activation、消息及清理 | 不重做，不作为创新 |
| 编排表达 | subagent、workflow的parallel/pipeline、工具执行与结果交付 | 复用，先测真实行为 |
| 固定保护 | 每棵activation树的容量与深度限制，工具并发上限 | 原生基线；单纯调参没有足够贡献 |
| 资源协调 | 多个工作流共享同一模型引擎时，合法工作的选择与推进时机 | 候选研究，尚未证明独立价值 |

DSH的“backend/provider”通常指子Agent执行提供方，不应直接等同于vLLM推理后端。Session在线不代表对应KV仍在GPU上；activation数量也不等于模型请求数。

## 一个可检验的研究问题

多个工作流共用引擎时，当前既可以启动新调查分支，也可以继续工具已返回的Agent，还可以完成最后一条必做分支触发父汇合。引擎只看到已提交请求；Harness知道已揭示依赖及工具状态。检验同时使用这些信息和真实引擎压力，是否比任何一边单独决策更好。

动作应落在合法边界：延后尚未启动的必做分支、选择哪个已有Agent进行下一次模型请求、在多工作流间分配可用推进机会；不任意中断正在生成的token，也不靠少做必做工作获益。优先“最后一条分支”只是必须比较的简单策略，不能预先视作新算法。前端等待全部计入任务耗时。

## 怎样才算论文贡献

改DSH是一种实现方式；能迁移的问题定义、必要的信息接口、非平凡决策机制与可信评估才构成研究候选。应先记录原生轨迹，证明真实并发、工具回流和外部负载确有损失，再给出解决机制。若普通优先级、固定窗口或同信息后端控制器已解释收益，应接受负结果，不能用“改了Harness”代替新颖性。

首个场景只选一种真实研究/核验任务，固定必做工作。比较DSH原生、调优静态控制、仅工作流信息、仅引擎信息、联合信息，以及同信息同动作权限的引擎侧协调器。评价完整任务平均与尾部耗时、任务正确性、实际token/工具工作量、背景任务影响和控制开销。动态改变Agent数量另做质量约束实验，避免混淆。

旧长短任务混合仅是资源异构诊断；没有真实DSH轨迹支撑时，不作为核心应用动机。安装验收也不等于完成了上述研究实验。

## 本次原生验收带来的修正

固定发行版 `0.2.1-rc.2` 的一个 HotpotQA 验收任务实际创建三个子 Agent。父 Agent 调用模型八次，三个子 Agent 各三次，标题服务另一次。孩子读文件后先 `send_message`，结束时框架还会交付完成通知；父 Agent 可在消息到达后继续请求模型。这说明真实执行是包含收件箱和重复唤醒的动态事件图，不能直接把旧的十调用 DAG 当作 DSH 原生行为。

但不能据此立即把“通知去重/父唤醒合并”包装成新贡献：DSH 的 `workflow` 已有 `parallel/pipeline` 与 caller delivery，能表达等待结果后统一汇合；文档明确，通知到达忙父 Agent 不会独立开始新请求。原生 `subagent` 与已有 `workflow` 两种模式必须都比较，差距有可能只来自应用写法。上述单题是人工指定三分片的功能验收，不是自然任务分布或负载损失的证据。

兼容提供方也已有 `vllmPriority`。单纯传优先级、限制 Agent 数、调一个静态窗口均不足以证明新颖性。当前原生配置未接入动态引擎遥测；记录用 HTTP 转发器也不做调度。引擎虽启用 priority scheduler，没有策略主动设置时仍不能称作前后端联合优化。

## 若继续研究，具体改哪里

建议在官方 DSH 加独立协调插件，优先复用扩展点；扩展点不足时再做最小源码补丁。保留 Session、收件箱、所有权、取消和资源清理语义。自建 Harness 继续作为受控对照，不替代真实系统证据。

| 位置 | 已有机制 | 候选增量与约束 |
|---|---|---|
| `agent/pre-step` | 异步准备下一模型步骤 | 在工具/消息交付后协调哪些 ready Agent 先推进；不能吞消息或改变任务的必做依赖 |
| `agent/request` | 请求前的异步配置扩展 | 为已有 ready 请求分配可取消的派发许可，记录前端等待；必要时携带阶段/依赖标签 |
| Subagent manager | activation 容量、父子关系、冷恢复、清理 | 复用生命周期事件；不把 GPU KV 与 Session/activation 数直接等同 |
| vLLM `/metrics` | 实际 running/waiting、KV 使用、抢占、前缀命中 | 作为动态观测输入；测量信息延迟、采样开销和过时反馈影响 |
| 多工作流协调 | 小组实验已实现跨CLI的FIFO基线协调器，联合推进机制未实现 | 只在已揭示的 ready 工作之间选择；若需要跨进程协调，单独说明部署假设 |

这些是已读源码中的可用接入位置，**候选的联合协调插件尚未实现或验证**。随后用户要求的最小八题组，已用 `agent/request` 实现仅限流及实际压力收缩的基线插件，未使用阶段进展改变排序，也没有控制分支展开；这不等于实现了上面的候选机制。特别是原生 activation 满额时明确拒绝而不排队，目的是防止父等待自身树中占用的名额。不能简单把 `reserve()` 改成无限等待队列；派发许可的等待、取消、名额释放和清理必须保持原来的活性要求。

一个聚焦的决策实例是：A 任务只剩一个必做分支，B 任务可继续扩展，C 的检索刚返回。引擎空闲时，过度串行会浪费并行机会；引擎排队或缓存紧张时，继续全面展开可能延迟 A/C 的有效推进。候选机制必须说明它在何种观测下切换这些选择，并胜过 FIFO、静态窗口、回流优先、汇合优先、原生 workflow 汇合，以及拥有同等信息/动作权限的后端控制器。不能提前知道工具何时返回或尚未生成的完整 DAG。

衡量的是从用户提交到所有必做分支及最终答案完成的总时间，前端等待也计入；同时核对正确性、实际 token/工具工作、其他任务受损程度和公平性。改变 Agent 数量、删减复核、换弱模型会改变工作量/质量，应放入另一组约束明确的实验，避免用少做工作解释调度收益。若简单基线已足够，则缩小或放弃这个候选问题。

## 关于论文表述

“修改 DSH”可以是系统论文的实现方式，和“修改 vLLM”一样，不能单凭依托现有开源系统判断有无论文价值。应写成“面向共享推理服务的 Agent 工作流推进协调”，将 DSH 作为一个实现和验证载体。能否抽象出跨 Harness 的状态接口、是否需要新的决策方法、与 INFRAMIND / Murakkab 的假设及动作空间到底差在哪里，仍须逐项核对；换框架或加 telemetry 都不是与已有工作的实质区别。目前没有足够证据宣称已构成顶会贡献。
